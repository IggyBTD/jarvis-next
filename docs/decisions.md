# Decisions

One line each. Newest at the bottom.

- D-01 Commits are per phase (P0..P12) on branch `jarvis-build`, not per step; each commit has a green `npm test`. A per-step history was not worth 65 commits for a single unattended pass.
- D-02 Folder: everything is built inside the existing JARVIS Next repo. The old front end in `src/` is kept (it is the HUD/chat app); the new server, agent and shared code are new top-level folders `server/`, `agent/`, `shared/`, `tests/`. The build brief's `next/` and `app/` folders do not exist here: `app/` maps to `src/` (see D-10).
- D-03 Config lives in `config/server/` because `config/` already holds files the old app imports with the same names (`models.json`, `actions.json`, `voice.json`).
- D-04 Browser sidecar is `sidecars/browser-guard/` because `sidecars/browser/` is the existing Intel-page sidecar; the existing one is untouched.
- D-05 Node 22+ (the dev machine runs 24). Test globs need it.
- D-06 Dependencies added: `ws`. `playwright` was already a dependency (the guarded sidecar uses it). Tests use `node:test` only.
- D-07 Thinking toggle: default `chat_template_kwargs: { enable_thinking: false }` in the request body, which llama-server and LM Studio pass to the Qwen3 chat template. `thinkingMethod` also supports `no_think` (appends `/no_think` to the last user message) and `request_field` (`reasoning_effort`). Verified only against the mock; confirm on the PC (HUMAN_TODO).
- D-08 Audit days are UTC dates. The chain spans days (first line of a day points at the last hash of the previous day).
- D-09 `actions.json` is generated once by `scripts/gen-actions.js` and is the contract afterwards (re-running keeps the `enabled` flags). Time tools (`set_timer`, `set_reminder`, `list_schedules`) are marked `internal`: they run on the server, not on an agent.
- D-10 Front end: the existing `src/` app is the client. A setting (Settings, "JARVIS server") switches it between its original local mode (LM Studio direct, local tools, this computer only) and server mode (the server owns the model, tools, approvals and conversation; the app draws what arrives). The two modes are exclusive, so two action runners never both reach a machine; in server mode a failed connection never falls back to local tools or the local model.
- D-11 The UI token is kept in localStorage in both the browser and the desktop build. An OS keychain needs a Tauri plugin or a Rust crate that cannot be built and checked unattended here, so it is a human step (HUMAN_TODO.md section 10). The global push-to-talk shortcut is likewise registered by the desktop build once voice (P9) is enabled.
- D-12 `wake_on_lan` exists as a Tauri command (src-tauri/src/wol.rs) because a browser cannot send UDP; the agent also has a `wake_on_lan` action for waking the other machine from a running one.
- D-13 The built app (`dist/`) is served by the JARVIS server itself, so a browser on the Mac needs nothing installed. A token in the URL #fragment is saved once and removed from the address bar (`scripts/client-link.js` prints the link). The static files hold no secrets; every data route still needs a token.
- D-14 The globe's aircraft data comes through the server in server mode (`server/osint/opensky.js`, routes under `/api/osint/`), because OpenSky refuses browser pages and the OpenSky login should stay on the PC. The old Intel sidecar keeps its own copy of the same logic and is untouched (the original local mode still uses it). Ship data (aisstream.io) is already fetched by the page itself, so its key is entered once per device.
- D-15 The Mac needs only a small bundle (`node scripts/make-mac-bundle.js`, about 80 KB): the agent, its sidecars, config and setup scripts, chosen from the real import graph. No Tauri app, no models, no tests, no tokens. Its prompt is `docs/MAC_PROMPT.md`.
- D-16 `machines.mac.host` in the PC's `config/server/machines.json` must be the Mac's address (the PC calls the Mac agent there); `server.url` in the Mac's copy must be the PC's address (OpenCode on the Mac reaches the model there). The server also listens on loopback, so the PC's own app works whatever its network address does.
- D-17 Saved chats in server mode are the server's conversations (`data/conversations/`): the sidebar lists, opens, renames, pins and deletes them through `/api/conversations`. `sessions.js` switches on `serverMode()`, so the original local mode (Rust store) is unchanged. The server keeps the chat; the window only remembers which one is open and redraws its last 30 messages on reload.
- D-18 Memory on the server is a short list of notes (`data/memory.json`, 50 notes of 300 characters) that the model writes with `remember` and removes with `forget`. They are shown on every turn as data from the user, never as instructions, and are tier T1 because the harm of a planted note is bounded by that framing and the cap; the user can read and delete them (`list_memories`, `forget`). The old Rust vault and instincts are not ported.
- D-19 The Mac updates itself with `node scripts/update.js`: it downloads `/api/bundle` from the server with its own machine token, unpacks it with a small zip reader, keeps `data/` and its own `config/server/machines.json`, runs `npm install` only if `package.json` changed, and restarts the LaunchAgent. The server builds the bundle on request (cached 60 s).
- D-20 The guarded browser tries the installed Google Chrome, then Edge, then Playwright's own Chromium, so no 150 MB download is needed. OpenCode is started as its real program (`opencode.exe` next to the npm shim on Windows), because a `.cmd` shim cannot be started without a shell.
- D-21 Not ported to server mode: plan mode and skills (local features of the original chat), a file tree and diff view of the other computer on the Code page (the Code page's task list shows the coding agent's tasks instead), the Rust memory vault. Voice engines on :8770/:8771 are a human step (HUMAN_TODO.md section 9).
- D-22 Waking a sleeping PC from another network needs a device on the PC's own network, so the design is a relay (`scripts/wake-relay.js`) that holds one MAC and one token and sends the Wake-on-LAN packet when asked over Tailscale; `scripts/wake.js` asks it and waits for the server's port. No port forwarding. Nothing here changes BIOS, adapter or power settings: `wake.js --check` only reads them. The packet code is shared (`shared/wol.js`) with the agent's `wake_on_lan` action.
- D-23 The LaTeX pad (Ctrl+L) converts symbol typing locally (`shared/latex.js`, no model, instant) and asks the model only when words are left over (`/api/latex` in server mode, the local model otherwise). The old Ctrl+L (jump to the message field) moved to Ctrl+J.

## 2026-10-25 Model tuning (27B vs Coder)
Qwen3.8-27B thinking is switched off with the top-level request field reasoning_effort none (chat_template_kwargs enable_thinking has no effect on this LM Studio). A thinking budget in the model's remembered settings (llm.prediction.reasoning.budgetTokens) works for API requests. Load settings that lms load has no flag for (KV cache type, MoE expert layers, batch size, thinking budget) are written into LM Studio's remembered per-model config, backed up in docs/lmstudio-settings-backup-2026-10-25. Recommended model: the 27B with thinking off and MTP 2 at 64k; see docs/bench-results-2026-10-25.md. models.json was not switched; only contextLength (65536) and the sampling block changed.

models.json now points at unsloth/qwen3.8-27b: thinkingMethod request_field with every use false (reasoning_effort none, also for OpenCode via the proxy), sampling 0.3 / 0.95 / 20 / 0 / 0 / 1.0, contextLength 65536, mtp.enabled true (documentation only; MTP is a load setting in LM Studio). Tests pin their own thinking policy (tests/helpers.js, p2-model, p7-digest) so they do not depend on which model models.json names.

## 2026-10-25 Model menu in server mode
The chip in server mode is now a working menu: GET /api/models lists what the PC's LM Studio has installed (loaded ones marked), POST /api/model loads the chosen model, unloads the others (409 while a reply is running), and switches the request settings to that model's profile in models.json (profiles; a model without one gets thinking off and LM Studio's own sampling). The choice is saved in data/active-model.json and applied at start. Only llm-client.js talks to LM Studio. The system prompt carries the date only; the time is added to the newest user message in the request (not stored), so the prompt prefix stays the same and LM Studio's prompt cache is reused.

## 2026-10-26 LaTeX mode replaces the LaTeX pad
D-23 is replaced: Ctrl+L no longer opens a window. It turns LaTeX mode on and off, with a "LaTeX" chip beside the input. In the mode, symbol-only text sent from the ordinary input is converted locally (`shared/latex.js`) and sent between $ signs; text with words is sent as typed. The /api/latex route stays but nothing in the app calls it.

## 2026-10-27 Permission modes for the coding agent
Five modes (shared/permission-modes.js): Auto (default), Manual, Accept edits, Plan, Bypass permissions. OpenCode now asks for every shell command and edit, so every request reaches the permission bridge, which applies the mode (`modeAnswer` in opencode-bridge.js) and audits each automatic answer with the mode named. The earlier OpenCode config that auto-allowed shell commands itself, and its destructive list, are replaced by this: Auto keeps the same effect (routine commands run, destructive ones ask) but is audited.
Bypass is not "nothing asks": T3 (outside the workspace, destructive commands, files that arm later commands such as package.json, git hooks and shell scripts) still asks in Auto, Accept edits and Bypass, because T3 is never automatic (policy.js). Plan answers read-only commands and fetches, refuses every edit and command that changes something, and puts a plan-mode note in front of each agent task. The mode lives on the server (data/permission-mode.json), is changed with the `mode.set` message and announced to every app. The chat model's own tool calls are not changed by the mode.

## 2026-10-27 Claude Code as an optional coding backend
Picking "Claude Code" in the model menu makes the official, unmodified `claude` program the coder for the Code page (`data/code-backend.json`; local models are picked from the same menu and put it back). A Code message then goes straight to a coding task (`agent-tasks.js` runClaude, `agent/sidecars/claude-manager.js`), and the run's result is written into the chat as the reply. Chat keeps using the local model.
Terms: the program is run on the person's own PC, signed in with their own login through Anthropic's own flow. JARVIS never reads, stores or passes on a credential, the agent's environment is cleaned (no API key), and nothing is offered to other users. Anthropic's terms do not clearly cover an app driving `claude -p` on a subscription all day (see the legal-and-compliance page); an API key is the risk-free option and would only need ANTHROPIC_API_KEY in the agent's environment.
Permissions: a headless run cannot ask, so what a mode would ask about is refused and reported ("n actions were refused"). `shared/claude-args.js` maps the five modes to flags and keeps the floors (destructive commands, shells, arming files); `--dangerously-skip-permissions` and bypassPermissions are never used, so Bypass equals Auto on this backend. Claude Code edits only inside the working folder. Not done: asking through the JARVIS gate (needs an MCP permission-prompt tool), live streaming of the text into the chat, resuming a session across messages.

## 2026-10-30 Google tools for the model (Calendar, Gmail, Drive)
Connecting a Google account on the Accounts page only stored a token; the model had no way to use it and fell back to the browser, which cannot sign in. Five read-only tools now exist (`server/core/google-tools.js`, defined in `actions.json`, category `google`): `google_calendar_events`, `google_gmail_search`, `google_gmail_read`, `google_drive_search`, `google_drive_read`. They run on the server for whichever machine is the target, so they are `internal` contract entries like `remember`.
- Tier T1 (auto in chat and in scheduled jobs). Nothing writes to Google: the scopes are `gmail.readonly`, `calendar.readonly` and `drive.readonly`, and no tool sends, labels, trashes, edits or shares. Results go through the router's untrusted wrapping, are size-capped (5000 characters of body, 20 items) and audited by name and arguments. Ids are checked against a pattern so a model-supplied id can never add a path segment to the Google URL.
- Without an `account` argument a call covers every connected account; one account failing is reported beside the others' results, all failing is an error. Calendar reads each account's primary calendar only.
- Adding `drive.readonly` means accounts connected before today have to be removed and connected again; Google cannot widen a stored grant. `drive.readonly` is a restricted scope, so the consent screen shows the unverified-app warning; that is fine for personal use (Publishing status In production, no verification submitted).
- The model is told in the base prompt to use these tools and never ask for a sign-in. A tool-selection category `google` (mail, calendar, drive words in English, Spanish, French) puts them in the request.
- Known risk, not new: mail and Drive text is untrusted data, but the browser tools are auto (T1), so a planted instruction could try to make the model open a page with data in its address. The wrapping and the browser sidecar's address checks are the only guards; if that matters, make `browser_navigate` ask once a `google_*` tool has been used in the same turn.
- The daily digest still reads the old single-account token (`data/tokens/google-token.enc`), which the Accounts flow never writes, so it shows its "not set up" banner. Not changed here.

## 2026-10-30 Fewer approvals, and working chats shown in the list
Why it asked so much: the audit log showed that with Auto mode on, the remaining asks were two things, both about the coding agent on this PC. (1) Any folder outside `C:\Users\bethe\jarvis-workspace` counted as "outside the workspace" (T3), including the Jarvis-Next folder the agent is asked to work on and the temp folder, so every read of `src\core\*` asked. (2) PowerShell commands longer than 400 characters (a web search through Invoke-WebRequest) were rated T3 for length alone. The chat model's own tools were already T0/T1 and never asked.
- `config/server/policy.json` `opencode.trustedFolders` (per machine) lists folders the coding agent may use as if they were its workspace: today the Jarvis-Next folder and the user temp folder on the PC. The project folder picked in the Environment card is trusted too. To trust another folder, add it there (a folder is trusted with everything under it; a sibling with the same prefix is not).
- Inside a trusted folder, an `external_directory` request is T2 and Auto, Accept edits and Plan answer it; outside, it is still T3 and always asks. T3 is still never automatic (policy.js) and the arming files (package.json, hooks, shell scripts, config files) still ask in every mode.
- New always-ask files, even inside a trusted folder: JARVIS's own safety code and keys (`server/core/policy.js`, `gate.js`, `audit-log.js`, `tool-router.js`, `auth.js`, `opencode-bridge.js`, `config/server/policy.json`, `data/tokens/**`). The agent can still change them; it asks first, which is the point.
- The command length limit is 1500 (was 400). Destructive patterns still match whatever the length. A command that only reads (single `Get-ChildItem`, `Get-Content`, `Test-Path`, `Select-String`, and similar PowerShell, plus the existing bash list) is allowed without asking in every mode, which also makes Plan mode usable on Windows. The "chained" check now also rejects parentheses and braces, because PowerShell runs a command inside `(...)`.
- Not changed: the browser sidecar asks the first time it types on a site, for unusual addresses and for submit-like clicks; `run_user_script` and anything T3 still ask. Manual mode asks about everything, as before.

Chat list: each row shows what the chat is doing, set in place without rebuilding the list. A ring that steps round for a chat the model (or a coding task) is working in, an amber dot where an approval waits for its task, an accent dot for a chat that finished while another was open (cleared when it is opened). A closed folder shows the most urgent state of its chats. The server says when each turn starts and ends (`chat.state`, plus a `running` list in the connection snapshot), the coding task carries its `convId`, and `src/core/chat-states.js` turns that into the marks (tested). The ring is the only thing that animates, only while a chat runs, in 8 steps a turn so the CPU-drawn window repaints a few times a second; with reduced motion it is still.
Leaving a chat that is still being answered (New chat, another chat, Code) no longer waits or refuses: the window lets go of it, the server keeps writing and saves the reply, and the list shows it working. If that chat is opened again when it finishes, the saved reply is read back. Clicking Code from another page starts a fresh chat; clicking Code while already on it, or going back to Chat, keeps the chat that is open. Not done: reopening a chat that is still mid-reply does not show the partial text; it appears when the reply is finished.

## 2026-11-15 Security fix run (docs/security/fix-run.md, progress in docs/security-fixes-progress.md)
- S-01 (F1-1) The permission bridge asks policy.decide (source "agent", with the permission mode and the request's class); `modeAnswer` moved to policy.js. In Auto only the read-only allowlist runs by itself; every other command asks. Bypass still answers T2 commands: it is the person's explicit choice, and T3 (now also interpreters, inline or encoded code, installs, registry and scheduler writes, matched anywhere in the command) asks in Bypass too. policy.json action overrides now accept `opencode_*` names. Tests that only existed to keep the old trust (`npm install` as T2, Auto answering any T2 command, the Claude backend allowing every command in Auto) were changed.
- S-02 (F1-1) The Claude Code backend cannot ask, so in Auto it now refuses every command outside the read-only allowlist instead of allowing all of them; Bypass keeps every command except the floors. Interpreters were added to the floors.
- S-03 (F1-1) Temporary taint flag: once a tool result is in a turn, `agent_task` asks (policy.js `ASK_WHEN_TAINTED`). Stage B replaces this with the tainted-turn rule.
- S-04 (F1-2) The read-only allowlist is parsed (shared/command-scope.js): each command has its own flag list, every path must resolve inside the workspace, UNC, device, provider (HKCU:, env:), drive-relative, home (~), 8.3 short and alternate-stream paths do not resolve, and a,b lists are two paths. policy.json `allowCommands` now names commands ("git status"); the old globs still load (a trailing * is ignored). `npm test` and `npm run test` left the list: they run code the agent may just have written.
- S-05 (F1-2) A command that is not read-only is T3 when it uses a variable or substitution, a quote that does not close, or names a path outside the workspace and trusted folders (cd is followed). In Auto it asks either way; the difference shows in Bypass and in the approval card. cmd-style %NAME% counts as a variable even under PowerShell, so `git log --format=%H%x09%s` asks.
- S-06 (F1-2) Manual asks for everything, read-only commands included. Plan runs nothing by itself: read-only commands, web fetches and trusted folders ask, everything that could change something is refused (refusing is stricter than asking, and keeps Plan's meaning).
- S-07 (F1-2) The Claude Code backend's prefix rules cannot check arguments, so only commands harmless with any argument become rules (shared/command-scope.js CLAUDE_SAFE: git status, git rev-parse, git branch alone, pwd, Get-Location, Get-Date, node and npm --version). It reads files with its own Read, Grep and Glob tools.
- S-08 (F1-3, decided by the owner before the run) The live JARVIS folder and the user Temp folder left `trustedFolders`. Everything under `cfg.root` and `cfg.dataDir` (and, on the other machine, the folders its agent reports in /info `jarvis_dirs`) is T3 and armed for the coding agent in every mode: edits, folder requests, reads and other path permissions, and commands that name such a path (resolved, or written out in the text). A chosen project folder does not open it. Plan refuses these instead of asking. The Claude Code backend gets `Read(//root/**)` and `Edit(//root/**)` deny rules in every mode. `.claude/**`, `.mcp.json`, `CLAUDE.md`, `dist/**` and `node_modules/**` joined the arming list. A web fetch of anything but http(s) is T3. Develop JARVIS itself with Claude Code, not with the JARVIS Code page on this folder.
- S-09 (F4-2) The machine resolves the coding agent's paths itself: a new system action `resolve_paths` (never offered to the model) follows links, junctions and 8.3 short names through the deepest existing part, drops Windows trailing dots and spaces, and returns null for what cannot be known. The bridge checks edits, folder requests, other path permissions and every word of a command that looks inside the workspace on paper against those real paths; no answer, or a null, is outside (T3). A Mac agent that has not been updated has no `resolve_paths`, so its coding agent asks for edits and commands until it updates.
- S-10 (F4-1) The sidecar routes and their methods live in one shared list (shared/proxy-routes.js), narrowed to what the server actually calls. The server checks it before sending and the agent checks it again on the raw address before forwarding: no percent encodings of any kind, no query strings, no dot segments, never the session command route, and a permission answer body must be exactly {reply|response: once|reject}. A machine token alone therefore reaches no OpenCode terminal, configuration or "always" answer.
- S-11 (F2-1) Markdown is sanitised by its own DOMPurify instance with a hook that keeps only data: and blob: sources (src, srcset, poster, background and the rest), drops ping, SVG image/use/feImage references to other documents, style attributes with url(), and style, link, meta and base tags. Links stay (a click is the person's own action). Pages the server serves get a CSP header and the Tauri window a CSP: images, media and fonts only from the app, data: or blob:. Scripts and styles may be inline because artifact frames are srcdoc documents that inherit the page policy and run charts inline under their own stricter policy; Tauri's own nonce and hash injection is switched off for script-src and style-src for the same reason (with a nonce present, 'unsafe-inline' would be ignored). connect-src is the serving host on server pages; in the desktop window it stays open (http:, https:, ws:, wss:) because the server address is chosen at run time; a fetch needs script, which the sanitiser keeps out. The artifact CSP meta is now at offset 0 of every HTML artifact.
- S-12 (F2-2, F2-5 for remember) The tainted-chat rule (server/core/taint.js, designed and written by a Fable sub-agent, docs/security/taint-design.md) replaces the stage-A flag. Every tool result except a short list of the machine's own readings and JARVIS's own data taints the chat; a call that was refused, denied or queued does not. Once tainted, addresses (browser_navigate) ask unless https and on policy.json browser.allowDomains (empty by default), page actions, agent_task, remember, write_file and run_user_script always ask, and any other call that carries text asks unless it only reads the person's own accounts or local files. The approval card shows every argument whole, the address and its parsed host first. Taint is stored on the chat and lasts as long as the chat (the model can repeat an injection in its own words, so no number of clean turns proves it gone); a new chat starts clean. Chats saved before the rule are derived from their history; machine-switch notices count, which only costs extra approvals in old chats. A tainted ask from a scheduled source is a deny. Task notes and Claude Code replies taint the chat they land in.
- S-13 (F2-4) Wrapped content has `<` written as `&lt;` before tool_call, think, function, tool and `<|` (chat template tokens), so quoted mail or pages cannot carry that markup. The model client stops reading `<tool_call>` text for good once the backend has answered with structured tool calls, and an inline call whose text already appears in a tool result or an untrusted block of the same request is dropped as an echo. The model test that read an inline call after a structured one was reordered: that sequence is exactly what is now refused.
- S-14 (F2-5) remember asks in a tainted chat (S-12). Every new note is broadcast (memory.added) and shown at once in the desktop chat and on the phone, whole, with an Undo button that calls forget through the router; removals are broadcast too (memory.removed). Saved notes reach the model inside an untrusted block. Notes saved before this change stay; the person sees them with list_memories and removes them with forget or the Undo of any new one.
- S-15 (F2-3) A task note holds one untrusted block, "agent task report", with the summary, each changed file on its own line (line breaks removed, 200 characters at most) and the failure reason on one line (300 at most). Only the task id, machine and state stay outside the block.
- S-16 (F2-7) A Claude Code reply on the Code page is stored as the assistant reply the person sees, marked origin "claude-code". When the history goes to the local model (conversations.js fit), that message becomes one line of the assistant's own plus the reply inside an untrusted block. The screen and saved chats are unchanged; replies stored before this change have no mark and stay as they were.
- S-17 (F1-7) The chat loop passes the names it offered the model in that request (ctx.offered); the router refuses any other name as unknown before it looks the tool up. Callers that are not the chat loop (the person's own direct calls, scheduled jobs, the voice path through the chat loop is covered) pass no list and are unchanged. A tool unlocked with list_action_categories becomes callable from the next request. The tainted-chat tests now use wording that offers the tool they exercise.
- S-18 (F3-1) Per-device pairing (server/core/devices.js, Fable) is wired: auth takes a UI token only as a paired device's token or the old shared token through the module's legacy path (tokens.ui and its rotation grace are no longer read by the server); every WebSocket message and REST route checks the device's scope (chat, approve, settings; Bypass, the trusted project folder, pairing, revoking others and the PIN need the desktop on the PC or the PIN); a T3 approval reads its tier from the gate, never from the message, and needs the desktop or the PIN; open sockets are re-checked every 20 seconds and right after an API revoke or rotation, and closed when their token no longer holds; the starter on 7411 checks the same store on every request. Any request through a proxy (forwarded or tailscale headers) counts as "proxied", never loopback. scripts/devices.js pairs, lists, revokes (legacy also replaces ui.token with no grace) and sets the PIN from the PC. Migration: the old shared token keeps working; from the PC itself it keeps the desktop's rights, from anywhere else it can chat and approve T0 to T2 only, until the owner revokes it.
- S-19 (F3-4) No token in any address, command line or Mac zip. The phone app, the phone's home-screen launcher (port 7411), the desktop page and open-mac.js each pair with a short code (node scripts/client-link.js phone|browser prints the codes; the phone needs two because the launcher and the app it opens keep separate storage) and keep their own token in their own storage. launch-app.js opens the plain address; the window keeps its paired token in its profile. open-mac.js updates with the Mac's machine token and rings the starter with its own paired token (node scripts/open-mac.js --pair CODE). make-mac-bundle --with-tokens no longer copies ui.token and warns. The existing dist-mac/jarvis-mac-with-tokens.zip is the owner's to delete (the run deletes no data). T3 approval cards on the desktop and the phone have a PIN field; the desktop window on the PC needs none.
- S-20 (F4-5) Every program the agent starts gets a clean environment (shared/child-env.js, Fable): only what a program needs to start, never a name that looks like a secret. Action arguments (JARVIS_A_*, JARVIS_ARG_*) are handed over on purpose; OpenCode gets its own OPENCODE_* variables and nothing of the agent's; Claude Code gets nothing secret (it signs in with its own login); the browser sidecar gets its own token. A permission that OpenCode reports as approved but JARVIS never answered trips an alarm: running tasks stop, an audit line is written, every client shows "Security: ...". Commands that print the environment, reach OpenCode's port 4096, or call DPAPI, Credential Manager or the Keychain are T3. scripts/jarvis.ps1 hands the Google token key to the server window only, by inheritance, never on a command line. Neither DPAPI nor the Keychain would stop a command running as the same user anyway; running OpenCode as its own user is the real fix (HUMAN_TODO.md section 12).
- S-21 (F3-2) The starter (7411) listens on the Tailscale address only, or on loopback when Tailscale is not up (never the LAN, never 0.0.0.0), accepts callers from the tailnet only (machines.json server.starterCallers narrows that to the phone and the Mac), has no loopback exemption, and blocks an address after 10 wrong keys for a minute. Its launcher page still needs no key (it holds none), behind the same caller check. New bind mode "tailscale" in shared/net.js: the Tailscale interface or loopback, never the LAN.

If Tailscale is down when the server starts, only the PC itself can reach it until a restart with Tailscale up.
- S-23 (F3-5) The phone approval sheet shows who asked, the summary, the exact request whole (no 1500-character cut, not folded away) with hidden characters revealed as [U+....] (shared/reveal.js, also used by the desktop dialog), what it would do and the screenshot. Approve stays off until the end of the request has been on screen; a request over 20 000 characters is answered on the desktop. Every audit line carries argsHash, a sha256 of the whole canonical arguments, so a stored string cut at 500 characters can be checked against the real request. A short secret inside a command could be guessed from that hash; F1-5's audit key is the place to turn it into an HMAC.

A Code-page message to Claude Code goes through router.invoke (agent_task), so it has its audit lines. - S-25 (F1-5) The audit chain is keyed: data/tokens/audit.key (made by the server, 0600) turns every new line into an HMAC (v: 2); older plain lines still verify, but an unsigned line after signed ones does not. head.json carries an HMAC tag and a count, and a mark with the same (data/tokens/audit.mark, outside data/audit) records how long the log was, so cutting entries, fixing head.json by hand or deleting the whole folder fails verify. The nightly audit-verify also checks anchors kept on the Mac (system actions audit_anchor and audit_anchors, append-only there) and sends a new one, and one is sent a minute after the server starts; an old Mac agent without these actions is skipped. A torn last line is still cut, and the cut is written into the log as an entry. A T2 or T3 action does not run when its "started" line cannot be written; the gate asks only once the question is in the log and denies otherwise; the permission bridge rejects instead of answering once when its line fails. The key is readable by the same OS user, so this holds against tools that edit files, not against code running as that user (HUMAN_TODO.md section 12).

Requests queued before this change carry no signature and are dropped at the next server start (they would have expired within 12 hours anyway).
